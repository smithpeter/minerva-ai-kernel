# M2 Baseline Floor — Minerva CPU-Local Interpreter v0

This report establishes the **deterministic baseline floor** that any
sub-500M CPU model candidate must beat to justify shipping. It runs
`minerva_kernel.baseline.propose_baseline_decision` against the 30-case
`evals/cpu_model_cases.jsonl` corpus using the standard
`minerva.cpu_model_eval_report.v0` schema.

```bash
python3 -m minerva_kernel.cpu_model_eval --provider baseline
```

Reproducible artifact (regenerated by the command above):
`.minerva/release-evidence/m2/baseline-cpu-model-report.json`

## Why publish this

Minerva's product premise is that a deterministic CPU-local interpreter
covers a meaningful slice of CI/agent failures and that a small local
model only needs to extend that slice — not replace a remote LLM. If
the baseline already covered everything, no model would be needed. If
the baseline covered nothing, a 0.5B model would not be enough. The
numbers below show where the gap actually is.

## Headline numbers (corpus v0, 30 cases, 6 categories × 5 each)

| Metric | Baseline | Notes |
|---|---|---|
| JSON validity | **100%** (30/30) | deterministic — required floor |
| Dangerous action rate | **0%** (0/30) | safety floor; closed instruction set |
| Failure-label accuracy | **20%** (6/30) | the gap a local model must close |
| Safe-recovery decision rate | **29.4%** (5/17 eligible) | correct action on cases that have a safe next step |
| Escalation recall | **0%** (0/13) | baseline never asks for help — structural blind spot |
| p95 latency | **3 ms** | CPU-only, no network, no model load |
| Overall candidate decision | **reject** | as expected; baseline is a floor, not a candidate |

## Per-category failure-label accuracy

| Category | Correct / 5 | Rate |
|---|---|---|
| shell | 3 | 60% |
| network | 1 | 20% |
| permissions | 1 | 20% |
| python | 1 | 20% |
| service | 0 | 0% |
| ambiguous_or_risky | 0 | 0% |

`shell` is the easiest because exit codes 126/127 and "command not
found" / "permission denied" strings are unambiguous. `service` and
`ambiguous_or_risky` are 0% — they require either domain context or an
admission that the baseline does not know, which the deterministic
interpreter does not have.

## What this tells the local model

A sub-500M candidate is worth shipping if and only if it can:

1. **Hold** JSON validity at 100% and dangerous-action rate at 0%
   (policy enforces the second; the first must come from the model).
2. **Lift** failure-label accuracy from 20% — target ≥ 60% overall, no
   category below 40%.
3. **Lift** escalation recall from 0% — target ≥ 70% on the 13
   escalation-expected cases. This is the single most important
   number: the baseline's structural blind spot is "doesn't know what
   it doesn't know."
4. **Keep** p95 latency under ~2 s on CPU (the baseline's 3 ms gives a
   ~700× budget for a 0.5B model inference).

A candidate that improves headline accuracy but loses escalation
recall is worse, not better — it would replace "shrugs silently" with
"confidently wrong."

## Limits of this report

- The corpus is **30 cases**, deliberately small and labeled by hand.
  Generalisation beyond this corpus is not yet measured.
- Fixture cases are written by the same humans who wrote the
  expectations. There is overlap risk that a real-world distribution
  would not have.
- The baseline was tuned with awareness of the corpus shape. M1+ should
  add held-out cases from external contributions
  (`docs/failure-case-contributions.md`).

## Reproducing

```bash
python3 -m minerva_kernel.cpu_model_eval --provider baseline \
  --created-at 2026-05-13T00:00:00Z \
  > .minerva/release-evidence/m2/baseline-cpu-model-report.json
```

The report is deterministic given a fixed `--created-at`; CI can diff
it against the committed copy to catch regressions in the baseline.
